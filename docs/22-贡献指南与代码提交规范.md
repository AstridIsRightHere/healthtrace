# 22 贡献指南与代码提交规范

> 本文为设计阶段协作规则，仅提供 Markdown 说明，不执行仓库初始化或任何 Git 操作。公开仓库只接收文档、代码与自造合成数据。

## 1. 贡献原则

贡献应服务于已确认的版本目标。MVP 技术方向为 Vue PWA、Spring Boot 和 MySQL，精确版本待 DEC-012 确认。开发、截图、测试、Issue、PR 与论文材料只使用自造合成数据，不使用真实报告改名、遮盖后的截图或真实患者记录。不得提交真实密钥、邮箱、邀请码、访问令牌、原始日志或其他个人信息。

设计中的成年人本人及子女、配偶代管必须基于有效授权。画像只控制文案，不能改变权限。任何贡献都不能让管理员默认查看健康内容，不能绕过邮箱验证、未验证上传限制或人工核实流程。

## 2. 建议贡献流程

1. 在 Issue 中描述问题、目标版本、验收条件与 FR、NFR、TC、ADR 或 DEC 关联；提交前检查正文和附件没有真实数据。
2. 确认工作属于已批准范围。涉及新收集目的、数据流、角色权限、删除行为、供应商、许可或版本归属的变化，先形成可评审的文档及决策记录。
3. 小步修改，并用合成数据验证相关成功、失败和边界路径；同步更新用户可见行为与文档。
4. 发起 PR，说明变更动机、验证证据、尚存限制和回退考虑；不直接向 main 推送。
5. 由项目发起人审阅；单人项目也需自审并留下记录。未完成的检查明确标为待验证，不能写成通过。

所有 Git 操作均须先解释具体目的、影响范围及风险，并取得用户确认后再执行。文档审批不等同于初始化仓库、创建提交、推送、合并或发布的授权。本文不包含 Git 命令。

## 3. 提交记录建议

提交标题采用“类型：简短中文目的”，必要时加范围，正文说明原因、影响、验证和关联编号。类型建议为：功能、修复、文档、重构、测试、维护。单次提交应围绕一个可解释的目的，避免把无关格式整理、功能与数据变更混在一起。

| 记录部分 | 应说明的内容 |
| --- | --- |
| 标题 | 用户或维护者能理解的变化，不夸大实现程度 |
| 原因与范围 | 为什么修改，影响哪个版本、页面或数据生命周期 |
| 追踪编号 | 如 FR-006、NFR-002、TC-006、ADR-004；待定事项用 DEC 编号 |
| 验证 | 已做检查、使用的合成场景、结果及未验证部分 |
| 数据影响 | 是否影响已有记录、审计、删除、恢复或供应商数据流 |

不得在标题、正文或评审附件中放入患者身份、检查数值、报告日期、图片、邮箱全文或密钥。

## 4. 代码规范（编码阶段适用）

本节只约定规范，不提供实现代码。前端使用TypeScript明确接口与状态类型，组件按页面与可复用职责拆分，避免把医疗结果格式化和可比规则散落在组件中；路由权限提示不能替代后端鉴权。统一格式与静态检查工具，具体配置在编码阶段评审。

后端按业务模块组织，控制层负责契约与输入验证、应用服务组织事务与权限、领域规则集中维护；不让控制层直接拼接数据查询。命名表达业务含义，类名、方法名遵循Java惯例；公开接口说明单位、日期与空值语义。禁止把密码、OCR正文或请求载荷放异常和日志。

数据库字段统一命名，关系与唯一约束需业务解释；数值使用十进制定点，日期与事件时间分开；索引基于实际查询与执行计划。迁移必须可审阅、评估兼容和回退，不手工改生产表后再补文档。禁止未经授权的跨档案关联。

测试覆盖规则与风险而非只追求覆盖率数字；外部依赖适配器可替换，单元测试不调用真实OCR/邮件；集成与E2E用合成数据。复杂决定注释解释原因，普通语句不重复注释。依赖最小化、锁定版本、定期安全更新，第三方许可核查。

提交类型统一采用docs/feat/fix/test/refactor/chore，分别对应文档、功能、修复、测试、重构、维护；中文描述目的，可带业务范围和Issue号，不要求在标题中包含全部追踪号。正式检查工具与精确版本待DEC-012，规范通过不表示现在允许编码。

## 5. 评审重点

| 类别 | 最低检查要点 |
| --- | --- |
| 业务 | 草稿须逐项确认才正式入图；OCR 失败进入待处理，拒绝 OCR 可以手填 |
| 图表 | 单位不换算；方法、标本分组；真实时间；非精确结果列表；前值零不算百分比、同日歧义不算结果间增减 |
| 身份 | 邀请与邮箱验证；未验证可登录但不能真实上传或找回；会话失效策略待确认 |
| 隐私 | 最小权限、账号隔离、管理员不可默认读内容；日志不承载健康内容 |
| 生命周期 | 列表移除、彻底删除、注销与撤回授权分别说明；备份和供应商残留不作未经验证的即时删除承诺 |
| 工程 | 合成样例、相关验收、错误路径、文档同步与预算影响 |

FR-001–FR-018 的功能验收对应 TC-001–TC-018；NFR-001–NFR-012 对应 TC-101–TC-112。测试范围根据变化确定，不用无关检查掩盖关键流程未验证。

## 6. 安全问题与公开协作

若发现泄露或越权风险，不在公开 Issue 粘贴原始内容。保留最低必要线索，通过待确认的人工渠道联系项目发起人，由其判断处置、通知与法定义务。若误提交秘密或患者信息，删除公开文本本身不等于风险消除，应评估凭据失效、访问范围和外部副本。

MIT 仅是许可证候选，DEC-010 确认前不宣称项目已采用该许可。任何软件或文档 License 都不授权患者数据的使用、传播或训练；第三方依赖、字体及资料各自的许可仍需核对。
